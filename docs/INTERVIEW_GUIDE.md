## 一、项目概述

### 1.1 项目背景

**问题**：运维团队面临告警量大、根因分析耗时长、知识分散难以复用等问题。

**解决方案**：构建智能运维诊断平台，通过 AI Agent + RAG 技术，实现自动化故障诊断和知识管理。

**核心价值**：
- 诊断时间从小时级缩短到分钟级
- 知识复用率提升，减少重复排查
- 降低对资深工程师的依赖

### 1.2 技术栈总览

| 层级 | 技术选型 | 理由 |
|------|---------|------|
| 后端框架 | FastAPI | 高性能异步、自动文档、类型提示 |
| 前端框架 | React + Semi Design | 字节出品、企业级组件库 |
| LLM 接入 | OpenAI / Claude API | 多后端支持、智能路由 |
| 向量数据库 | Qdrant | 高性能、支持过滤、开源 |
| 图数据库 | Neo4j | 知识图谱、关系推理 |
| 缓存 | Redis | 会话管理、结果缓存 |
| 文件存储 | MinIO | S3 兼容、私有化部署 |

```
┌─────────────────────────────────────────────────────────────┐
│                    Orchestrator (编排器)                     │

│                                                             │

│  │   顺序执行   │  │   并行执行   │  │   层级执行   │        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
│                                                             │
│  ┌─────────────┐                                          │
│  │   DEBATE    │  ← 多 Agent 辩论，选出最优方案            │
```

**四种协作模式：**

| 模式 | 场景 | 优势 |
|------|------|------|
| Sequential | 复杂诊断流程 | 结果可预测，便于调试 |
| Parallel | 简单查询、快速响应 | 响应时间短 |
| Hierarchical | 多层级分析 | 层级间并行，效率高 |
| Debate | 争议性问题 | 多角度分析，结果更可靠 |

### 3.2 LangGraph 状态机设计

```python
# 状态定义
class AgentState(TypedDict):
    messages: List[Dict]      # 对话历史
    intent: str               # 识别的意图
    knowledge: str            # 检索到的知识
    tool_results: Dict        # 工具调用结果
    reasoning: str            # 推理过程
    response: str             # 最终响应
    confidence: float         # 置信度

# 状态流转
[Start] → [Router] → [Knowledge] → [Tools] → [Reasoning] → [Output] → [End]
               │           │           │
               └───────────┴───────────┘
                     ↓
              条件分支路由
```

**面试要点：**

**Q: 为什么用状态机而不是简单的流水线？**

A:
1. **灵活性**：可根据中间结果动态调整流程
2. **可观测性**：每个状态变化都可追踪
3. **容错性**：单个节点失败可重试或降级
4. **可扩展**：新增节点不影响现有流程

**Q: ReAct 模式是什么？如何实现的？**

A:
ReAct = Reasoning + Acting，交替进行思考和行动：

```
循环:
1. Thought: 分析当前状态，决定下一步
2. Action: 执行工具调用或检索
3. Observation: 观察执行结果
4. 重复直到完成任务

实现：
- max_steps 限制最大循环次数
- is_complete() 判断是否完成
- 工具结果反馈到下一轮推理
```

### 3.3 智能路由设计

```python
class LLMRouter:
    """
    根据任务类型选择最优模型
    
    路由策略:
    - 简单查询 → GPT-3.5 / Claude Haiku (快速、低成本)
    - 代码生成 → Claude Opus / GPT-4 (代码能力强)
    - 复杂诊断 → GPT-4 / Claude Opus (推理能力强)
    - 中文任务 → 中文优化模型
    """
    
    def select(self, prompt: str, task_type: TaskType) -> Tuple[str, str]:
        complexity = self.estimate_complexity(prompt)
        
        if task_type == TaskType.CODE:
            return "claude", "claude-3-opus"
        elif task_type == TaskType.SIMPLE and complexity < 0.3:
            return "openai", "gpt-3.5-turbo"
        else:
            return "openai", "gpt-4o"
```

3. **结果标准化**：LLMResponse 统一响应格式
4. **故障转移**：主后端失败自动切换备用

## 四、RAG 知识检索

### 4.1 混合检索架构

```
用户查询
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│                    Query Optimizer                           │
│  查询重写 → 同义词扩展 → 关键词提取                          │
└─────────────────────────────────────────────────────────────┘
    │
    ▼
┌───────────────────────┐    ┌───────────────────────┐
│     Vector Index      │    │    Keyword Index      │
│    (语义相似检索)      │    │    (BM25 精确匹配)    │
│     Qdrant            │    │    rank-bm25          │
└───────────────────────┘    └───────────────────────┘
    │                               │
    └───────────────┬───────────────┘
                    ▼
┌─────────────────────────────────────────────────────────────┐
│                    Fusion Retriever                          │
│           RRF (Reciprocal Rank Fusion) 排序融合             │
└─────────────────────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────────────────┐
│                    Reranker (可选)                           │
│              Cohere / BGE-Reranker 重排序                   │
└─────────────────────────────────────────────────────────────┘
                    │
                    ▼
               Top-K 结果
```

**面试要点：**

**Q: 为什么用混合检索而不是单一检索？**

A:
| 检索方式 | 优势 | 劣势 |
|---------|------|------|
| 向量检索 | 语义理解、发现隐含关联 | 精确关键词可能遗漏 |
| 关键词检索 | 精确匹配、关键信息不丢 | 无语义理解 |
| 混合检索 | 兼顾语义和精确 | 实现复杂度高 |

实际测试中，混合检索召回率提升 15-20%。

**Q: RRF 融合算法原理？**

A:
```python
def rrf_fusion(results_list, k=60):
    """
    Reciprocal Rank Fusion
    
    公式: score(doc) = Σ 1/(k + rank(doc))
    
    k 是平滑参数，默认 60
    """
    scores = {}
    for results in results_list:
        for rank, doc in enumerate(results):
            doc_id = doc.id
            scores[doc_id] = scores.get(doc_id, 0) + 1/(k + rank + 1)
    
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

```
文档上传 → 格式识别 → 解析提取 → 智能分块 → Embedding → 存储
                │

        └───────────────────────────────────────┘
```

**面试要点：**

**Q: 分块大小如何选择？**

A:
1. **太小 (100-200)**：上下文不完整，语义断裂
2. **太大 (1000+)**：检索精度下降，噪声多
3. **推荐 300-500**：平衡上下文完整性和检索精度
4. **overlap 10-20%**：保证边界信息不丢失

**Q: 如何处理表格和图片？**

A:
1. **表格**：转换为 Markdown 表格或 JSON 结构
2. **图片**：OCR 提取文字 + 图片描述生成
3. **图表**：提取数据 + 文字描述

## 五、评估体系

### 5.1 RAGAS 评估指标

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| Faithfulness | 回答是否基于上下文 | 回答中的陈述在上下文中有支持的比例 |
| Answer Relevancy | 回答是否切题 | 回答与问题的相关性分数 |
| Context Recall | 检索是否完整 | 上下文包含标准答案关键信息的比例 |
| Context Precision | 检索是否精确 | 检索内容中与问题相关的比例 |

### 5.2 诊断评估指标

```python
@dataclass
class DiagnosisMetrics:
    root_cause_accuracy: float    # 根因准确率
    solution_relevance: float     # 方案相关性
    time_to_diagnosis_ms: int     # 诊断耗时
    knowledge_hit_rate: float     # 知识命中率
    agent_count: int              # Agent 调用次数
```

**面试要点：**

**Q: 如何量化评估 Agent 效果？**

A:
1. **自动化评估**：RAGAS 指标 + 自定义指标
2. **人工评估**：专家打分、用户反馈
3. **A/B 测试**：对比不同策略效果
4. **持续监控**：线上指标实时追踪

**Q: 如何改进低分指标？**

A:
- Faithfulness 低 → 改进检索质量、优化 Prompt
- Relevancy 低 → 加强意图理解、改进答案生成
- Recall 低 → 扩大检索范围、优化查询扩展
- Precision 低 → 添加重排序、优化检索排序

```python
async def parallel_retrieval(query):
    # 向量和关键词检索并行
    vector_task = asyncio.create_task(vector_search(query))
    keyword_task = asyncio.create_task(keyword_search(query))
    return await asyncio.gather(vector_task, keyword_task)
```

**Q: 如何处理高并发请求？**

A:
1. **异步 IO**：FastAPI + asyncio，单进程处理大量并发

3. **缓存**：热点数据 Redis 缓存
4. **限流**：防止系统过载

## 七、难点与解决方案

### 7.1 技术难点

| 难点 | 解决方案 |
|------|---------|
| 多 LLM 后端一致性 | 统一抽象层 + 标准化接口 |
| 检索召回率低 | 混合检索 + 查询扩展 |
| Agent 推理不稳定 | ReAct 循环 + 自我反思 |
| 知识更新不及时 | 增量索引 + 版本管理 |
| 评估体系缺失 | RAGAS 框架 + 自定义指标 |

### 7.2 面试高频问题

**Q: 项目中遇到的最大挑战是什么？**

A:
**挑战**：Agent 推理结果不稳定，同一问题多次回答不一致

**解决**：
1. 引入 ReAct 循环，强制 Agent 分步推理
2. 添加自我反思机制，验证推理过程
3. 降低 temperature 参数，减少随机性
4. 构建评估体系，持续监控效果

**Q: 如何保证知识库数据质量？**

A:
1. **数据清洗**：去重、格式标准化
2. **质量评分**：文档完整度、时效性评估
3. **反馈机制**：用户标注无效文档
4. **定期更新**：过期文档自动标记

**Q: 如果用户反馈回答不准确，如何改进？**

A:
1. **收集反馈**：点赞/点踩、详细评价
2. **案例分析**：定位失败原因（检索/推理/生成）
3. **针对性优化**：
   - 检索问题 → 扩展知识库、优化检索
   - 推理问题 → 改进 Prompt、调整模型
   - 生成问题 → 模板优化、后处理
4. **回归测试**：确保优化不影响其他场景
